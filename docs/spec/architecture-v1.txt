======================================================================
1. CONCEPT
======================================================================

Projects 6, 7, 8, 9, 10, 11 and 13 can be combined into one coherent product.

Working product name:
NexusPC

Alternative names:
- SystemDesk
- PC Sentinel
- SysGuard
- Workstation Command Center
- DeviceOps Desktop

The idea is NOT to mash seven programs into one executable without structure.
Instead, build one C++ platform with a shared desktop shell and separate modules.

NexusPC would be a local-first computer management, protection, diagnostics,
storage, backup, network, and information-retrieval suite.

All seven projects share the same operating environment: the user's computer.

They also share infrastructure:

5. PROCESS / SECURITY ARCHITECTURE
======================================================================

Recommended evolution:

PROCESS 1: nexuspc-ui
- Qt desktop application
- User-facing dashboard
- Starts/stops jobs
- Displays reports and alerts

PROCESS 2: nexuspc-agent
- Optional background service
- Hardware sampling
- Network polling
- Connectivity checks
- Backup schedules
- Search indexing
- File scan jobs

PROCESS 3: nexuspc-vault
- Optional isolated vault process
- Minimal API
- Keeps decrypted secret material outside general monitoring modules
- Locks independently

Communication:
- Local IPC only by default
- Named pipes / Unix domain sockets / local RPC abstraction
- Authenticated local session
- No remote management enabled by default

9. CROSS-MODULE INTELLIGENCE
======================================================================

The combined suite becomes more valuable when modules cooperate without breaking
security boundaries.

Examples:

1. Duplicate Finder + Backup
Before backing up 400 GB, Storage Intelligence can report that 70 GB are exact
duplicates. The user may clean them first.

2. Hardware Health + Backup
If disk health indicators or repeated IO failures degrade, NexusPC can recommend
running an immediate verified backup.

3. Internet Monitor + Backup
Network/cloud backup jobs can pause when connectivity is unavailable or below a
user-defined threshold.

4. Network Center + Internet Monitor
The system can distinguish:
"your PC cannot reach the router"
from
"the router is reachable but the internet is down."

5. Search + Backup
Search results can show whether a file is included in the latest backup snapshot.

6. Search + Duplicate Finder
Duplicate groups can link directly to indexed documents and metadata.

7. Hardware Health + Storage
Low disk-space alerts can offer:
- inspect large folders;
- run duplicate scan;
- adjust backup retention.

10. UNIFIED FUNCTIONAL REQUIREMENTS
======================================================================

UFR-001: The user shall have one dashboard for all installed modules.
UFR-002: Modules shall be independently enableable/disableable.
UFR-003: Background jobs shall be scheduled through one job system.
UFR-004: Long-running jobs shall support progress and cancellation.
UFR-005: Modules shall publish alerts through one notification center.
UFR-006: Reports shall be accessible through one report center.
UFR-007: The system shall maintain an audit trail for destructive/admin actions.
UFR-008: Filesystem exclusions shall be reusable across scan/index/backup modules.
UFR-009: The platform shall expose common machine and storage information once.
UFR-010: The system shall support per-module data-retention settings.
UFR-011: The Vault shall remain isolated from non-vault modules.
UFR-012: Remote management shall be disabled by default.
UFR-013: Destructive storage actions shall be reversible where the OS permits.
UFR-014: Scheduled jobs shall survive application restart.
UFR-015: The agent shall operate with minimum permissions needed.
UFR-016: The user shall be able to export system and module reports.
UFR-017: Resource-intensive jobs shall support CPU/disk/bandwidth throttling.
UFR-018: The platform shall avoid running conflicting heavy jobs simultaneously
         unless the user allows it.
UFR-019: The system shall provide centralized configuration and diagnostics.
UFR-020: Module failures shall not crash unrelated modules.

13. WHAT HAPPENS TO PROJECT 12?
======================================================================

Keep #12 Mini Database Engine SEPARATE.

Reason:
The Mini Database Engine is an educational systems/database project. Using your
own early-stage database as the persistence layer of NexusPC would create
unnecessary reliability and data-loss risk.

For NexusPC:
Use SQLite/PostgreSQL.

For your portfolio:
Keep the Mini Database Engine as an independent deep technical project proving
that you understand:
- parsing;
- storage pages;
- indexes;
- buffer management;
- query execution;
- transactions/recovery.

Later, once the mini database is mature, you could build an experimental branch
of NexusPC that uses it for non-critical telemetry, but it should not be the
initial production storage engine.
